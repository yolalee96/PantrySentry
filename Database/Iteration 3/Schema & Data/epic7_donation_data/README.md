# Epic 7 – Food Donation Centre Data## OverviewThis folder contains the static data prepared by the Data Team for **Epic 7 – Food Donation** in PantrySentry.Epic 7 supports the food donation workflow by allowing users to:- discover available donation centres;- view donation centre information and donation requirements;- search and sort donation centres using location information;- view the food types accepted by each donation centre;- match household food items with suitable donation centres.The Data Team provides verified static reference data for donation centres and their accepted food types.---## FilesThe Epic 7 static data deliverables contain **two CSV files**:| File | Records | Database Table | Purpose ||---|---:|---|---|| `donation_centres.csv` | 27 | `donation_centres` | Stores donation centre information, location, contact details, operating information and verification source. || `donation_centre_accepted_foods.csv` | 190 | `donation_centre_accepted_foods` | Stores the food types accepted by each donation centre. |These two files contain the static reference data required from the Data Team for Epic 7.---## 1. Donation Centres`donation_centres.csv` contains **27 donation centres**.The file follows the agreed Data Team structure for `donation_centres` and contains **19 columns**.The dataset includes information such as:- centre ID;- organisation name;- organisation type;- description;- donation requirements;- address;- city;- state;- postcode;- latitude and longitude;- phone number;- email;- website;- operating hours;- active status;- verification source;- created and updated timestamps.The donation centre information was collected from available organisation websites and other referenced sources.Where available, `verification_source_url` records the source used to verify the donation centre information.---## 2. Accepted Food Data`donation_centre_accepted_foods.csv` contains **190 accepted-food records**.The file follows the agreed 8-column structure:```textneed_idcentre_idcategory_iditem_namenotesis_activecreated_atupdated_at```Each record represents a food type accepted by a particular donation centre.A donation centre may therefore have multiple accepted-food records.The accepted-food data is intended to support matching between household food items and donation centres that accept the corresponding type of food.---## 3. Data RelationshipThe two static datasets are linked through `centre_id`:```textdonation_centres.centre_id            ↓donation_centre_accepted_foods.centre_id```Each accepted-food record must reference an existing donation centre.The `category_id` in `donation_centre_accepted_foods.csv` references the existing PantrySentry product categories.Valid category IDs are:```text1, 2, 3, 4, 5, 6, 7, 8,11, 12, 13, 14, 15, 16, 17, 18```Category IDs `9` and `10` do not exist and must not be used.The current accepted-food dataset uses the following category IDs:```text1, 2, 4, 6, 7, 12, 13, 14, 15, 18```All category IDs used in the dataset are valid.---## 4. Organisation TypesThe `organisation_type` field follows the values supported by the Epic 7 database structure.Allowed values are:```textCARE_HOMENGOFOOD_BANKCOMMUNITY_CENTRERELIGIOUS_ORGPANTRY_DROP_OFFCOMMUNITY_FRIDGEOTHER```The current dataset uses:```textCARE_HOMEFOOD_BANKNGOPANTRY_DROP_OFF```All organisation types used in the dataset are valid.Only organisation types that apply to the verified centres are included. The dataset does not create additional records simply to cover every possible enum value.---## 5. Data VerificationDonation centre information and accepted-food information were collected from available organisation websites and referenced sources.The following principles were applied during data preparation:1. Donation centre information should be traceable to a referenced source where possible.2. Accepted food should only be added where sufficient supporting information is available.3. Unsupported accepted-food requirements are not invented.4. Food categories are not added solely to increase dataset coverage.5. Notes are based on available source information rather than assumptions.6. If a source confirms that an organisation accepts food donations but does not provide sufficiently specific accepted-food information, unsupported accepted-food records are not created.Therefore, some donation centres may have no detailed accepted-food records.This does **not automatically indicate missing or incorrect data**. It may indicate that sufficiently specific accepted-food information could not be verified from the available source.This approach avoids unsupported assumptions and keeps the dataset traceable to available evidence.---## 7. Category MappingEach accepted-food record is mapped to an existing PantrySentry product category through `category_id`.Examples include:| Accepted Food | Category ||---|---|| Fresh vegetables | `4 – Vegetables` || Packaged beverages | `7 – Beverages` || Canned food | `13 – Condiments, Sauces & Canned Goods` || Rice | `14 – Grains, Beans & Pasta` || Eggs | `18 – Eggs` |The mapping uses the existing PantrySentry category structure.`item_name` and `category_id` were checked for semantic consistency.Where an accepted-food description is broad, a category is assigned only when the relationship is sufficiently clear.---## 8. Notes and Donation RequirementsThe `notes` and `donation_requirements` fields provide additional information where supported by the source.Some records may share similar notes because the same donation requirement applies to several accepted food types at the same centre.More specific requirements are not added unless they can be supported by the available source.For example, requirements such as:```textPreferably pull-tab cans.```or:```textAt least 3 months shelf life remaining.```should only be included when the source actually specifies those requirements.The Data Team does not add such conditions solely to make the notes more detailed.---## 9. Location Data`donation_centres.csv` includes latitude and longitude values to support location-based donation centre discovery and distance sorting.The database uses:```textlatitude  DECIMAL(10,7)longitude DECIMAL(10,7)```Coordinates in the final dataset are therefore stored with no more than **7 decimal places**.For example:```text2.0683822102.5852908```This precision is sufficient for donation-centre distance calculations.The backend may use these coordinates with the Haversine formula or an equivalent distance calculation.---## 10. CSV Format and Data QualityThe final static CSV files use:```textEncoding: UTF-8 without BOM```Timestamps follow MySQL `DATETIME` format:```textYYYY-MM-DD HH:MM:SS```For example:```text2026-10-03 12:00:00```Optional empty fields should be imported as SQL `NULL` where appropriate.Text fields containing commas, quotation marks or line breaks follow standard CSV escaping rules.For example:```csv"Canned food, packaged beverages, and packaged food are preferred."```A field containing a line break must remain enclosed in double quotation marks so that it is treated as one CSV field rather than multiple records.The final datasets were checked for:- valid CSV structure;- valid `centre_id` relationships;- valid `organisation_type` values;- valid `category_id` values;- coordinate precision;- timestamp format;- accepted-food/category semantic consistency;- UTF-8 encoding without BOM.---## 11. Runtime Donation TablesEpic 7 contains four database tables:```textdonation_centresdonation_centre_accepted_foodsdonation_recordsdonation_record_items```However, the Data Team provides static data only for:```textdonation_centresdonation_centre_accepted_foods```No CSV files are provided for:```textdonation_recordsdonation_record_items```This is intentional.`donation_records` and `donation_record_items` contain **runtime user-generated data**, rather than static reference data.### `donation_records`This table is populated when users create donation requests through the application.It stores information related to the donation request, such as:- team;- donation centre;- user;- donation status;- drop-off window;- declaration agreement;- donation completion time;- notes.### `donation_record_items`This table is populated when users select inventory items to include in a donation.It stores information such as:- donation;- inventory item;- donated quantity;- unit;- food condition;- expiry date at donation;- photo information;- related inventory transaction.Because these records depend on actual user actions and household inventory, they should be created by the application during normal system operation.Therefore:- no placeholder data is provided;- no test data is included in the static dataset;- no empty CSV templates are included in the Data Team deliverables.---## 12. Donation and Inventory BehaviourCreating a donation request does not immediately remove an item from the user's inventory.The intended workflow is:```textUser selects food for donation        ↓Donation request created        ↓Status = PENDING        ↓Inventory remains unchanged        ↓Donation completed        ↓Status = COMPLETED        ↓DONATE transaction created        ↓Inventory updated```When a donation is `PENDING`, the corresponding inventory remains unchanged.When a donation is successfully `COMPLETED`, the application creates the corresponding `DONATE` inventory transaction and updates the inventory.A `CANCELLED` donation does not change the inventory.Donated food is not treated as consumed food or discarded food and should not generate a waste-impact assessment.---## 13. Import OrderThe Epic 7 static data should be imported in the following order.### Step 1Import:```textdonation_centres.csv```into:```textdonation_centres```### Step 2Import:```textdonation_centre_accepted_foods.csv```into:```textdonation_centre_accepted_foods```This order is required because `donation_centre_accepted_foods.centre_id` references `donation_centres.centre_id`.`donation_records` and `donation_record_items` are not part of the Data Team static-data import process.---## 14. Import ValidationAfter importing the static data, the following checks can be used.### Donation centre count```sqlSELECT COUNT(*)FROM donation_centres;```Expected:```text27```### Accepted-food record count```sqlSELECT COUNT(*)FROM donation_centre_accepted_foods;```Expected:```text190```### Orphan accepted-food records```sqlSELECT COUNT(*)FROM donation_centre_accepted_foods afLEFT JOIN donation_centres dc    ON af.centre_id = dc.centre_idWHERE dc.centre_id IS NULL;```Expected:```text0```### Invalid category IDs```sqlSELECT DISTINCT category_idFROM donation_centre_accepted_foodsWHERE category_id NOT IN (    1,2,3,4,5,6,7,8,    11,12,13,14,15,16,17,18);```Expected:```text0 rows```### Organisation types```sqlSELECT DISTINCT organisation_typeFROM donation_centresORDER BY organisation_type;```Current dataset:```textCARE_HOMEFOOD_BANKNGOPANTRY_DROP_OFF```### Centres without detailed accepted-food records```sqlSELECT    dc.centre_id,    dc.name,    COUNT(af.need_id) AS accepted_countFROM donation_centres dcLEFT JOIN donation_centre_accepted_foods af    ON dc.centre_id = af.centre_idGROUP BY dc.centre_id, dc.nameHAVING accepted_count = 0;```A result from this query does not automatically indicate an error.A centre may have no accepted-food records when sufficiently specific accepted-food information could not be verified from the available source.---## 15. Data Quality PrinciplesThe Epic 7 static dataset follows these principles:- use verifiable donation-centre information;- preserve source traceability through `verification_source_url`;- do not invent accepted-food requirements;- do not invent more specific notes without source support;- do not add categories solely to increase dataset coverage;- use existing PantrySentry product categories;- maintain valid `centre_id` relationships;- maintain valid category references;- keep coordinates compatible with the database schema;- use UTF-8 without BOM;- keep runtime user donation data separate from static reference data.The objective is to provide sufficient verified data to support Epic 7 while avoiding unsupported assumptions.---## 16.
